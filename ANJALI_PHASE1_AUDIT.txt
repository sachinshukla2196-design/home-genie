5. DATABASE PROBLEMS (hard-delete recreate ROOT CAUSE)
=====================================================================
- Products & categories re-seed on restart (server.py:126-136).
  Categories are re-created by name every boot; the Starter Kit product
  is re-seeded whenever the products collection is EMPTY. So if an admin
  hard-deletes all products/categories, they REAPPEAR after a
  backend/deploy restart. This is the residual "records come back" root
  cause. Distributors, orders, wallets, commissions do NOT re-seed
  (safe).
- demo_seed.py exists but is NOT imported/called anywhere (dormant dead
  code). Not a current cause, but a latent risk if ever wired in.
- PII stored in plaintext: users.aadhaar_number and
  kyc_records.pan/aadhaar/bank_account are unencrypted at rest
  (compliance concern).

=====================================================================
6. SECURITY PROBLEMS
=====================================================================
- HIGH — Mock OTP exposes codes in beta. .env has APP_ENV="beta",
  OTP_PROVIDER="mock". providers.otp_create returns dev_otp (the real
  code) in the API response for non-production. Because /login-otp/send
  returns the code and /login-otp/verify logs you in by mobile, anyone
  can take over any account by mobile number while APP_ENV != production.
  /register and /change-mobile are similarly exposed. In
  APP_ENV=production the mock is blocked with 503, which then BREAKS
  those flows since no real SMS provider is wired.
- P1 — JWT in localStorage (lib/api.js:7, context/AuthContext.js:11,27):
  XSS token theft risk.
- MEDIUM — Withdrawal balance check is non-atomic
  (wallet_routes.py:260-265): concurrent requests could over-withdraw
  (read-then-write, no conditional update).
- MEDIUM — No Razorpay server webhook. Payment confirmation relies on the
  client calling /payments/razorpay/verify; RAZORPAY_WEBHOOK_SECRET is in
  env but UNUSED — a dropped client callback leaves a genuinely-paid
  order unmarked until manual admin action.
- LOW — JWT_SECRET has a hardcoded dev fallback (core.py:29) if env is
  missing.
- LOW — Rate limiting only on login (5 attempts); no throttle on
  OTP/registration/withdrawal endpoints.
- Positives: all admin routes gated by require_admin; order access has
  ownership/admin check (no IDOR); admin passcode uses
  hmac.compare_digest; payment amounts are server-side.
