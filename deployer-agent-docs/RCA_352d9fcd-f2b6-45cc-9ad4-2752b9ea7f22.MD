# RCA — anjali-ayurveda-mvp redeploy failure (run 352d9fcd-f2b6-45cc-9ad4-2752b9ea7f22)

## Outcome
Redeploy FAILED at step `deploy_k8s` (rollout never became ready → health check 111 Connection refused on `/health`). The app was NOT taken down — the previous healthy run (`4f139512…`, deployed 2026-09-12) is still live at https://anjali-ayurveda-mvp.emergent.host.

## Root cause (confirmed, not guessed)
The FastAPI backend crashes on startup, so nginx has no upstream and the pod never passes readiness.

Container log (verbatim):
```
RuntimeError: CORS_ORIGINS is not configured with explicit production origin(s).
  File "/app/backend/server.py", line 58, in <module>
Backend died, shutting down nginx...
```

The source (read from the failed run's pulled code) at `backend/server.py:56-58`:
```python
_cors = [o.strip() for o in os.environ.get("CORS_ORIGINS", "").split(",") if o.strip() and o.strip() != "*"]
if not _cors:
    raise RuntimeError("CORS_ORIGINS is not configured with explicit production origin(s).")
```
This guard **filters out the literal `*`** and then raises if no explicit origin remains.

The production `CORS_ORIGINS` secret is set to `*`. Confirmed via `list_secrets` with an expected-value check: `CORS_ORIGINS` → `matches_expected: true` for value `"*"` (value never revealed, is_empty=false). After the guard strips `*`, the list is empty → RuntimeError → process exit.

This guard is NEW since the last successful deploy (2026-09-12). The older code accepted `*`; the current source rejects it (also correct behavior — `allow_origins=["*"]` with `allow_credentials=True` is invalid per the CORS spec).

## Why a plain redeploy cannot fix this
On redeploy, **pre-existing production secret values are NOT overwritten**. So `CORS_ORIGINS` stays `*` and the backend crashes identically on every retry. The preview `backend/.env` only carries `CORS_ORIGINS="https://herbal-life-hub.preview.emergentagent.com"` (a preview URL, and it would not overwrite the existing prod secret anyway). Re-running `resume_pipeline` was therefore intentionally NOT done — it would fail the same way.

## The fix (user action — fastest, recommended)
Update the `CORS_ORIGINS` secret VALUE in Deployment Panel → Secrets to explicit production origin(s) (comma-separated, no `*`), then redeploy. Based on this deployment's live URL + verified custom domains, the correct value is:
```
https://anjali-ayurveda-mvp.emergent.host,https://anjaliherbal.life,https://www.anjaliherbal.life
```
Save, then redeploy. The backend will boot and the rollout will pass readiness.

## Alternative (code — not recommended)
Relaxing the `server.py` guard to allow `*` would get it to boot but is insecure and invalid alongside `allow_credentials=True`. Keep the guard; fix the secret value instead.

## Scope notes
- `deploy_k8s` is the failing *step*; the true cause is the app boot crash above (a config/secret fault).
- Not a manifest fault — no manifest change was made.
- Not reproducible in the eph sandbox (no secrets injected there); diagnosis is from the failed run's logs + source read + a confirmed secret-value match, not a full in-pod boot.
