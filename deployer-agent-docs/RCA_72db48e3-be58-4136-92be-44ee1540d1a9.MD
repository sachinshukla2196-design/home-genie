# RCA — anjali-ayurveda-mvp deploy failure (run 72db48e3-be58-4136-92be-44ee1540d1a9)

## Verdict
Deploy failed at **deploy_k8s / health_check**. The pod's nginx came up but the FastAPI backend **died on boot**, so `/health` returned connection-refused (111) until the rollout timed out ("deployment failed to become ready"). This is a **secret/config fault**, not a source or manifest fault.

## Root cause (verbatim from the rollout logs)
```
Backend died, shutting down nginx...
RuntimeError: CORS_ORIGINS is not configured with explicit production origin(s).
  File "/app/backend/server.py", line 60, in <module>
    raise RuntimeError("CORS_ORIGINS is not configured with explicit production origin(s).")
```
`backend/server.py` intentionally refuses to boot when `CORS_ORIGINS` is `*` or empty. This is the guard the user asked us NOT to loosen — so it is working as designed. The production `CORS_ORIGINS` secret currently holds a value the guard rejects.

## Evidence
- Confirmed on the live run via `list_secrets` (with expected-value check): `CORS_ORIGINS` → `is_empty=false`, **`matches_expected=false`** against the intended `https://anjaliherbal.life`. So the key exists but holds the wrong value (e.g. `*` or stale), which the guard rejects.
- The same `RuntimeError: CORS_ORIGINS ...` killed the three preceding redeploy attempts (12:47, 13:21, 21:59 on Oct 1) — a consistent, deterministic boot crash, not a transient infra issue.
- A failed run is never promoted: the live app is still the last healthy run (`4f139512`, `https://anjali-ayurveda-mvp.emergent.host`) — it is NOT down.

## Why a plain redeploy will NOT fix this
`CORS_ORIGINS` is a **pre-existing deployment secret**, and pre-existing secret values are **NOT overwritten** by a redeploy that pulls the preview `.env`. So re-running the pipeline will fail identically until the stored value is changed. The value must be edited in the UI.

## Required fix (user action — I cannot do this; no secret-write tool)
1. **Deployment Panel → Secrets → edit `CORS_ORIGINS`** to an explicit production origin list and Save, e.g.:
   `https://anjaliherbal.life,https://www.anjaliherbal.life`
   (user's stated intent is `https://anjaliherbal.life`; both custom domains `anjaliherbal.life` and `www.anjaliherbal.life` are verified on this deployment, so include www if browsers hit it).
   Do NOT set it to `*` or blank — that is exactly what the guard rejects.
2. **New keys** `MSG91_ENABLED=false` and `EMERGENT_LLM_KEY` are not present in production yet. As NEW keys they are picked up automatically from preview `backend/.env` on the next redeploy — confirm they are present in preview `.env` before redeploying.
3. **Redeploy** after the `CORS_ORIGINS` value is saved.

## What was NOT changed
Guard left intact (per user instruction). No source edit, no manifest edit, and I did not re-run the pipeline — re-running without the secret fix would just reproduce this crash.
